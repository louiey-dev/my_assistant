# API design

Date: 2026-09-01

## Conventions

- Base path: `/api/v1`
- Content type: `application/json`
- Timestamps: UTC ISO 8601 strings
- Resource identifiers: stable device or camera identifiers
- List endpoints use `limit`, `offset`, and time-range query parameters where
  applicable.
- Commands are asynchronous and return a request identifier.

## REST endpoints

### Health and system

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/healthz` | Process health check; does not require authentication |
| `GET` | `/api/v1/status` | Backend, broker, database, and streaming status |

### Devices and sensors

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/devices` | List devices with current availability |
| `POST` | `/api/v1/devices` | Register a device |
| `GET` | `/api/v1/devices/{device_id}` | Get device details |
| `PATCH` | `/api/v1/devices/{device_id}` | Update device metadata |
| `DELETE` | `/api/v1/devices/{device_id}` | Remove a device and its configuration |
| `GET` | `/api/v1/devices/{device_id}/readings` | Query sensor readings |
| `POST` | `/api/v1/devices/{device_id}/commands` | Send a device command |

### Cameras

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/cameras` | List cameras and stream capabilities |
| `GET` | `/api/v1/cameras/{camera_id}` | Get camera details |
| `PATCH` | `/api/v1/cameras/{camera_id}` | Update camera metadata |
| `POST` | `/api/v1/cameras/{camera_id}/commands` | Send a PTZ or camera command |
| `GET` | `/api/v1/cameras/{camera_id}/stream` | Return an authorized WebRTC/HLS stream descriptor |

The API must never return RTSP credentials or embed them in a response.

### Command request

```json
{
  "command": "camera.ptz",
  "parameters": {
    "pan_degrees": 10,
    "tilt_degrees": 0,
    "zoom": 1
  }
}
```

Successful command submission returns `202 Accepted`:

```json
{
  "request_id": "01JXYZ1234567890",
  "status": "queued"
}
```

## WebSocket

Connect to `/api/v1/ws`. The server sends JSON event envelopes:

```json
{
  "type": "sensor.reading",
  "timestamp": "2026-09-01T07:16:00Z",
  "data": {}
}
```

Initial event types:

| Event | Purpose |
| --- | --- |
| `sensor.reading` | New sensor measurement |
| `device.state` | Device metadata or state changed |
| `device.availability` | Device connected or disconnected |
| `camera.state` | Camera connection or stream state changed |
| `command.status` | Command queued, succeeded, or failed |

Clients may send a subscription message to limit events:

```json
{
  "type": "subscribe",
  "devices": ["office-sensor-01"],
  "cameras": ["office-camera-01"]
}
```

The server must close the connection with a documented error code when the
client sends invalid JSON or an unsupported subscription.

## Error responses

Use one consistent JSON shape for all non-success responses:

```json
{
  "error": {
    "code": "device_not_found",
    "message": "The requested device does not exist.",
    "request_id": "01JXYZ1234567890"
  }
}
```

Initial error codes:

| HTTP status | Code | Meaning |
| --- | --- | --- |
| `400` | `invalid_request` | Malformed or invalid input |
| `401` | `unauthorized` | Authentication is required or invalid |
| `403` | `forbidden` | User is not allowed to perform the operation |
| `404` | `not_found` | Resource does not exist |
| `409` | `conflict` | Operation conflicts with current state |
| `422` | `unsupported_command` | Device does not support the command |
| `429` | `rate_limited` | Too many requests |
| `500` | `internal_error` | Unexpected backend failure |
| `503` | `dependency_unavailable` | Broker, database, or camera service unavailable |

Error messages must not reveal credentials, stack traces, or internal file
paths. Include a server-generated request or correlation identifier in logs.
